# Jam documentation

The documentation site is a React application built with Vite. The authored
documentation is versioned Markdown under `docs-content/`; the application and
Markdown renderer live under `src/`.

## Prerequisites

- Node.js 22
- npm
- Python 3.10 or newer, used to generate the API reference

From this directory, install the dependencies with:

```bash
npm ci
```

The deployment workflow also uses npm and `package-lock.json`, so use npm when
changing dependencies.

## Run the site locally

```bash
npm run dev
```

This generates the API reference and the application data before starting the
Vite development server. Markdown files are converted into generated
TypeScript and JSON rather than imported directly. If you edit Markdown while
the server is already running, regenerate that data in another terminal:

```bash
npm run docs:build
```

Vite will then reload the changed generated files.

## Where things live

| Path | Purpose |
| --- | --- |
| `docs-content/<version>/` | Authored Markdown for a released documentation version |
| `docs-content/nav.yml` | Shared sidebar structure and page labels |
| `scripts/gen_api.py` | Generates the latest API reference from `src/jam/` |
| `scripts/build-docs.ts` | Builds navigation, rendered pages, and the search index |
| `src/generated/` | Generated application data; commit updates to these files |
| `src/components/MarkdownRenderer.tsx` | Supported Markdown rendering behavior |
| `src/App.tsx` | Documentation site layout, routing, and search |

## Edit an existing page

Most changes should be made in the highest version directory under
`docs-content/`. That directory is exposed through the `/latest/` route.

For example:

```text
docs-content/4.2.0/authx/jose/jwt.md
```

Only change an older version when correcting documentation for behavior that
was already present in that release. Do not update every historical version
for a feature that only exists in the latest release.

After editing, run:

```bash
npm run docs:build
npm run build
```

Commit the Markdown and the resulting changes under `src/generated/`.

## Add a page

1. Create a Markdown file in the appropriate version directory. Use lowercase,
   descriptive paths, for example:

   ```text
   docs-content/4.2.0/authx/new-mechanism.md
   ```

2. Start the document with one level-one heading:

   ```markdown
   # New mechanism
   ```

3. Add the page to `docs-content/nav.yml`:

   ```yaml
   - block: Authentication
     pages:
       - label: New mechanism
         file: authx/new-mechanism.md
   ```

   Usually the new item should be added to an existing block rather than
   creating another block.

4. Run `npm run build` and open the page from the sidebar. Also search for a
   phrase that appears only in the body to confirm that it was indexed.

`nav.yml` is shared by every documentation version. The build includes a page
in a version only when the referenced file exists in that version, so a
latest-only page does not need placeholder files in older versions. Avoid
renaming or removing an existing entry without considering its historical
versions and URLs.

## Markdown conventions

The renderer supports standard Markdown, GitHub-flavored Markdown tables and
task lists, fenced code blocks with syntax highlighting, and admonitions.

Use fenced code blocks with a language:

````markdown
```python
from jam import Jam
```
````

MkDocs-style admonitions are supported. Their body must be indented by four
spaces:

```markdown
!!! warning "Keep keys private"
    Never put secret key material in documentation examples.
```

Supported admonition types are `note`, `tip`, `warning`, `danger`,
`deprecated`, and `info`.

Use relative links for nearby pages when that keeps the reader in the selected
version. For links intended to follow the current documentation, use
`/latest/<path>`. Do not hard-code a release version unless the link is
deliberately version-specific.

Examples must not contain real credentials, tokens, private keys, or usable
secrets. Prefer complete, runnable examples and explain security-relevant
defaults and failure behavior.

## API reference

Do not edit `docs-content/<latest-version>/api/` by hand. It is ignored by Git
and generated by `scripts/gen_api.py` from public modules, classes, functions,
methods, signatures, and docstrings under `src/jam/`.

To improve generated API documentation, update the corresponding public
docstring in the Python source and run:

```bash
npm run docs:build
```

Older API references are not regenerated; they remain tied to their release.

## Add a documentation version

When preparing a release:

1. Create `docs-content/<new-version>/` using the previous version as the
   starting point, excluding its generated `api/` directory.
2. Update the copied Markdown for the new behavior.
3. Keep existing paths where possible so external links remain valid.
4. Update `nav.yml` only for actual navigation changes.
5. Run `npm run build` and commit the new version plus `src/generated/`.

Version directory names must be stable semantic versions such as `4.3.0`.
Pre-release names are not discovered by the build. The highest version becomes
the target of `/latest/`.

## Build and validation

Use the full production build before opening a pull request:

```bash
npm run build
```

It performs the following steps:

1. Generates the API reference from the Python package.
2. Builds the navigation manifest, page components, and full-text search
   index.
3. Produces the Vite application in `dist/`.
4. Generates and verifies static entry points for versioned and `/latest/`
   routes.

Before submitting a documentation change, check that:

- the page appears in the expected sidebar and version;
- internal links and heading anchors work;
- code blocks and admonitions render correctly;
- body text can be found through search;
- `src/generated/` contains the expected regenerated changes only;
- `npm run build` succeeds.

Do not commit `dist/`, `node_modules/`, or generated API files under
`docs-content/<version>/api/`.
